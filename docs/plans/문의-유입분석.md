# 문의 유입·여정 분석 작업 계획   (2026-11-22 합의: 옛 관리자 "문의 상세"의 [유입 및 퍼널 여정 분석] 블록을 새 사이트에 적용)

목표: 참관 신청·협업 문의가 들어올 때 **어디서 왔고(채널·유입 출처), 어떤 페이지를 거쳐(최초 진입 → 탐색 경로), 얼마나 머물다(체류 시간), 어떤 기기로(모바일·앱) 신청했는지**를 함께 저장하고, 관리자 문의 카드에서 보여 준다.

## 설계 결정
- 옛 사이트와 같은 **서버 없는 방식**: `journey.js` 가 세션 첫 방문 정보(리퍼러 호스트·진입 경로·UTM·기기·인앱 브라우저)와 페이지 이동 이력·체류 시간을 `sessionStorage` 에 기록한다. 외부 분석 도구(GA4) 없이 동작하며, 나중에 GA4 를 붙여도 이 데이터는 그대로 쓴다.
- 저장은 **별도 컬럼 `journey jsonb`** 로 한다. 옛 사이트처럼 문의 내용(message)에 글자로 붙이면 신청자가 쓴 글과 섞여 검색·정리가 어렵다. 관리자 화면에서는 보기 좋게 글자로 풀어 보여 준다.
- 채널 분류 규칙(리퍼러 호스트 기준): naver(검색·블로그·카페·지도), google, daum/kakao, instagram/facebook/youtube, 그 외 사이트 = 외부 링크, 리퍼러 없음 = 직접 입력·명함 QR. UTM 이 있으면 그 값을 우선한다(`utm_source/medium/campaign`).
- 개인 식별 정보는 넣지 않는다(IP·세밀한 기기 식별 없음). 경로·시간·기기 종류·리퍼러 호스트만.
- 관리자·테스트 트래픽 제외: `?journey=off` 또는 localStorage 플래그로 기록을 끈다(옛 사이트의 `?bni_ga=off` 와 같은 역할).

## 위험 요소
- GitHub Pages 정적 글 페이지는 `<base href="../../">` 를 쓰므로 경로 기록은 `location.pathname` 기준으로 통일(예: `/blog/슬러그/`). 도메인 루트·github.io 하위경로 둘 다 같은 형식이 되도록 `/bni-choegang-web` 접두어는 떼고 저장.
- sessionStorage 는 탭 단위라 새 탭에서 열면 새 세션으로 기록됨(옛 사이트와 동일한 한계).
- 네이버 앱·인스타 인앱 브라우저는 리퍼러를 안 주는 경우가 많아 "직접 입력"으로 잡힐 수 있음. UA 로 인앱 여부는 따로 표시한다.
- 옛 "퍼널 도달 STEP 1→6" 문구는 실제 측정값이 아니라 고정 문장이었음. 새 사이트에서는 실제로 아는 것만 적는다(착륙 → 탐색 N페이지 → 폼 제출).
- `journey jsonb` 컬럼은 Supabase 프로젝트 생성 전에 schema.sql 에 넣어야 한 번에 끝남. 이미 실행한 뒤라면 alter 문 한 줄 추가 실행.
